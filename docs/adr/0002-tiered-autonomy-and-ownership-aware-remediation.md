# ADR-0002：以分级自治和所有权感知执行器扩展诊断闭环

| 状态 | 决策日期 |
|---|---|
| 已采纳 | 2026-08-08 |

## 背景

ADR-0001 已决定把 QQ 群显式报障与 NoneBot 本机运行证据关联，但若产品只停在“定位并生成报告”，
维护者仍需手工判断能否改配置、怎样重启、应向哪个上游报告，以及本地插件是否值得直接修复。用户已确认
NoneBot Triage Agent 应继续深入到修复闭环，同时保留 Bot 维护者的最终控制权。

这些动作的风险并不相同：读取结构化运行证据是本机只读动作；修改配置和重启会改变在线实例；创建
GitHub Issue 会代表维护者与外部社区交互；修改插件代码还会引入供应链、测试和部署风险。因此不能把它们
合并成一个拥有 Shell、文件系统与 GitHub Token 的无限制 Agent。

## 决策

NoneBot Triage Agent 采用“责任层路由 + 分级自治 + 动作专用执行器”的产品架构。

### 责任层路由

每个支持会话先把当前问题归入可修订的责任候选，而不是直接选择工具：

1. Bot 生命周期或配置；
2. 第三方插件；
3. 本地插件或维护者拥有的插件；
4. NoneBot 框架、适配器或外部平台；
5. 证据不足，继续最小补证。

路由结论必须附带证据与置信限制；新增证据可以改变责任层，不能把第一次模型判断当作不可变事实。

### 自治能力阶梯

| 等级 | 能力 | 默认权限 |
|---|---|---|
| L0 观察 | 关联事件、Matcher、插件、平台 API、异常与版本证据 | 自动，但严格最小化与有界保留 |
| L1 建议 | 生成诊断、补证问题、配置差异、重启或上游报告草稿 | 自动生成，不能执行 |
| L2 实例修复 | 应用配置变更、重启 Bot、健康检查与必要回滚 | 每个动作显式审批 |
| L3 上游协作 | 查重并以维护者授权身份创建或补充 Issue | 目标与最终正文显式审批 |
| L4 代码修复 | 为本地或维护者拥有的插件生成补丁并运行隔离测试 | 补丁与测试可自动，合并或部署另行审批 |
| L5 验证发布 | 部署候选修复、观察健康状态并闭环 SupportCase | 暂不进入近期范围 |

首个 MVP 采用逐动作显式审批，不把一次批准扩张为长期授权。后续若引入预授权策略，必须按 Bot 实例、
动作类型、目标资源和有效期单独建模。

### 执行边界

- 模型只能提出类型化的 `RepairPlan`，不能直接获得 Shell、配置文件或 GitHub 写权限；
- 配置执行器必须生成字段级差异，建立可恢复备份，使用目标应用的 schema 校验，原子替换，并把重启作为
  独立待批动作；健康检查失败时按已记录变更集回滚；
- 生命周期执行器只调用部署者显式配置的进程管理适配器，不猜测 `systemd`、Docker、进程管理器或裸进程；
- 上游协作执行器先检索重复 Issue，再生成含环境、最小复现、脱敏证据和责任不确定性的草稿；必须使用
  维护者主动授权的身份，披露自动生成辅助，并由维护者确认仓库、标题和最终正文；
- 代码修复只作用于本地插件或维护者明确声明拥有的仓库，在隔离工作区或 Runner 内生成补丁并运行测试；
  不在正在服务的 Bot 进程中原地改第三方插件源码；
- 所有建议、批准、执行、验证和回滚都写入顺序审计事件，并绑定同一个 SupportCase、证据快照和变更集。

## 选择理由

- “责任层”决定应该建议配置修复、联系上游还是修改本地代码，能把 Agent 能力与真实维护流程对齐；
- 分级自治让低风险证据采集可快速发生，同时把在线变更与外部身份行为保留给维护者；
- 动作专用执行器比通用 Shell 更容易限定输入、测试失败路径、记录审计和实现回滚；
- 诊断、执行、健康检查与结果验证形成可展示的业务闭环，也自然引出 Bot 实例、插件安装、审批、变更集和
  验证记录等持久化实体，而不是为了“显得有数据库”附加无关 CRUD。

## 否决的替代方案

### 给单个 Agent 完整 Shell、文件系统和 GitHub 权限

权限边界过宽，外部报障文本可能间接影响高风险动作，也难以证明每次变更的输入、批准和回滚关系。

### 群友报障后自动创建上游 Issue

普通用户只观察到现象，未必能确认责任插件；自动写回会放大误报、重复、隐私泄露和社区维护成本。

### 直接修改运行中实例的配置或插件源码

缺少备份、校验、隔离测试和健康检查，失败后无法可靠恢复，也会把观察进程与执行进程的故障域混在一起。

### 永久停在诊断和报告

可以降低查日志成本，但无法验证诊断是否真正解决问题，也不足以形成维护者可委托的完整工作流。

## 结果与约束

产品将自然形成以下长期领域实体：`BotInstance`、`PluginInstallation`、`SupportCase`、`EvidenceBundle`、
`RepairPlan`、`Approval`、`ChangeSet`、`Verification` 与 `UpstreamReport`。它们说明后续需要持久化和并发控制，
但本 ADR 不提前选择数据库或部署形态。

当前实现只具备离线 Case / 会话控制面与 L0/L1 的部分基础。首个实施切片只建立传输无关的结构化运行观察
契约和显式容量 / 保留策略的内存缓冲，不接入真实 NoneBot、模型、配置写入、进程重启、GitHub 写回或代码
修改。以下问题必须在对应高权限切片开始前冻结：

- 运行证据的默认保留时长、最大容量、群内告知和管理员导出策略；
- 每类副作用的审批持久化、超时、撤销和预授权范围；
- 支持的配置格式、秘密值提供方式、备份位置和回滚健康判据；
- GitHub 身份授权、自动生成披露、查重阈值和跨仓库路由规则；
- Bot 进程管理适配器、维护者所有权声明和隔离 Runner 边界。
