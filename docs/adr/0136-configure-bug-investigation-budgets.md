# ADR-0136：由部署者配置 Bug 调查预算

> 已由 [ADR-0130](0130-finalize-production-agents-before-hard-budget-exhaustion.md) 替代。当前生产 Bug 调查使用固定的请求、证据、输出、时间、token 与费用边界，并在硬上限前显式进入收尾阶段；下文保留为历史决定。

| 状态 | 决策日期 |
|---|---|
| 已采纳；正式 Bug 入口继续暂停 | 2026-09-13 |

## 问题

Bug 调查沿用历史 OpenCode 实验的 800 单次输出额度，并派生出 7,200 累计输出限制。分页案例在缩小首轮目录后，累计 69,576 tokens 已低于 120,000 总量限制，却因 9,880 输出 tokens（包含思考）再次被截停。插件分发后，不同模型、资料规模和调查难度无法共用这组写死的额度。反复要求先降低消耗才能继续验证，掩盖了调查本身能否完成的问题。

## 决定

- 优先提供足够资源验证调查能力，消耗优化独立进行；正常工作量超出额度时可以提高配置，不以优化到旧额度内作为继续推进的条件。
- 沿用 NoneBot 配置入口，增加四项独立 Bug 配置：总超时默认 300 秒、单次生成默认 16,384 tokens、累计输入输出默认 300,000 tokens、通用工具默认 6 次。它们是可调整的起始默认值，不是通用最优值；仅校验正数与有限超时，模型支持额度由实际 Provider 合同决定。
- 模型请求上限随通用工具次数取 `工具次数 + 3`，保留独立聊天窗口、最终输出及一次输出修正，默认 9 次。Toolbox、Agent 及 SDK 的并行溢出反馈上限使用同一个配置；既有单类工具与正文限制保持有效。
- 删除由单次生成额度乘请求次数得到的累计输出限制，取消默认美元限制。累计 tokens 根据 Provider 报告的各次输入输出求和，包括缓存输入；不包含前序路由和 Answer。SDK 通常在响应后检查，不能承诺严格的账单上限。
- 工具按实际证据需要使用，足够时结束，不要求耗尽额度。不按插件名称或成员数量分配特殊额度，不增加难度分类模型、自动扩额、失败重跑或动态预算调度器。
- 当前 Prompt v14 仅去掉固定“六次”描述，改为共享本轮额度。预算值形成独立版本指纹，参与模型资格匹配，不能沿用不同额度的已验证标签。
- 联合理解、Answer 和 Behavior 的预算不变。预算耗尽继续按 `analysis_unavailable` 结束，不得解释为不存在 Bug；正式入口、登记及副作用边界保持不变。

本决定当时部分替代 ADR-0050 的固定费用预算方向，以及 ADR-0135 保持旧预算与固定六次上限的约定；资料快照、按需读取和证据检查不变。

## 依据与适用边界

[Anthropic 的研究 Agent 工程实践](https://www.anthropic.com/engineering/multi-agent-research-system)按查询复杂度分配工作量；[Effort 文档](https://platform.claude.com/docs/en/build-with-claude/effort)区分简单任务和复杂推理的投入。[Task budgets 文档](https://platform.claude.com/docs/en/build-with-claude/task-budgets)建议在额度引发提前停止时先提高预算，并观察代表性任务的实际消耗再调优。

这些资料支持推进原则，不构成跨 Provider 的统一预算协议。Claude 的任务预算是给模型的软提示，统计口径不同于 SDK 累计输入输出；本项目不直接搬用其参数或数字。插件体积影响资料成本，问题难度影响推理与取证次数，两者不能由成员数量单独推断。

## 落实与确认

配置到生产 Agent 工厂、Runtime Toolbox 和 SDK UsageLimits 的传递链同步调整。程序验证覆盖环境配置、向上调整、不同预算不复用资格、超过旧累计输出及美元额度时正常完成、超时与累计 token / 请求次数耗尽时无额外模型调用，以及提高工具额度后仍能完成最终输出修正。

真实分页复测使用同一份实际初检与用户补充、冻结的公开资料及只读插件源码，单独记录结果，不伪造线上观察或日志。实测结果不能证明任意规模插件或所有 Bug 调查已经通过。

落实后的程序回归为 278 项通过、1 项因 Windows 符号链接不可用跳过；Ruff 和修改模块类型检查通过。真实分页单次复测由正式配置工厂创建 Agent，4 次模型请求、6 次通用取证，33.78 秒，输入 73,936、输出 6,189（其中思考 5,804），累计 80,125 tokens。最终候选 `unknown / insufficient_evidence` 经生产协调器接受，缺失运行观察及关联日志；本轮无预算异常、登记或平台发送。此轮输出低于旧累计输出阈值，不将一次随机生成结果用作旧限制因果影响的唯一证据；对应超旧额度行为由程序回归独立覆盖。


### 2026-09-13：默认取证额度调整

项目作者随后接受默认通用取证从 6 次提高到 12 次，模型请求上限同步从 9 次提高到 15 次。上述首次实测仍保留原 6 次预算，不把该运行改标为 12 次验证。

成员目录与成员详情工具原来还在工具可见性层分别引用固定默认次数，导致部署者提高总额度后仍可能提前隐藏；现已删除这两项重复限制，直接共享部署配置的通用额度。回归覆盖 6、12、20 次配置，两种成员读取均可超过旧默认上限，最后仍保留输出及一次修正。其他单类工具限制本次只核查，不扩大访问范围。

核查发现：源码搜索两次、文件读取一次后会在后续模型轮次隐藏对应工具，可能妨碍多文件调查；设计搜索两次、无参数快照工具一次及独立聊天窗口一次同样存在。它们由 SDK prepare 控制后续可见性，不应被描述成对同一响应中并行重复调用的严格单类计数拦截。通用总额度仍在工具体 / Toolbox 中检查。

源码读取另有每次搜索最多扫描 256 个合格 Python 文件、返回 6 个命中、单文件 256 KiB 等限制。证据正文累计仍为 120,000 字符，与模型 300,000 tokens 预算分别计数。总调用预算提高不等于这些覆盖边界已经解除。

本次相关回归 222 项通过、1 项 Windows 符号链接不可用跳过，Ruff、修改模块类型及空白检查通过。历史 v8 evaluator 与 CLI 显式固定其六次取证合同，避免生产默认值变化改写历史题目的含义；这不是对当前模型组合重新资格化。本轮没有再调用真实模型，前述分页实测仍只代表当时六次预算下的运行。

### 2026-09-13：源码搜索与多文件读取共用总额度

项目作者接受移除源码搜索两次、文件读取一次的独立限制。两类工具共用默认 12 次通用取证，模型仍最多 15 次请求；Prompt v15 同步允许入口委托其他模块时继续定位和读取，保留不虚构路径、不重复读取已有完整内容的要求。批准根、单文件大小、累计正文、模型 tokens 与超时不变；256 文件扫描范围另行处理。

程序回归 202 项通过、1 项 Windows 符号链接不可用跳过。新增测试通过真实 Runtime、SDK 工具编排、只读源码读取器和协调器，使用两份临时源码验证入口到处理模块的读取、第三次源码搜索，以及 4/5 次小预算耗尽后工具隐藏并正常输出 unknown；模型响应用替身控制，以稳定触发边界。另以真实安装的 meme 源码和合成 gif分解问题进行一次真实模型验证，结果单独记录。

真实模型首次实际搜索五次、完整读取两个文件，8 次模型请求、12 次取证，累计 304,788 tokens，最终因超过默认 300,000 被 SDK 拦截。保留该失败记录，按既定原则只把本次验证累计额度提高到 600,000 再运行；Prompt、问题、模型设置和共同输入散列保持不变，插件默认仍为 300,000。第二次通过四次搜索、一次完整文件读取及辅助模块片段完成调查，4 次模型请求、11 次取证、67.08 秒，累计 156,702 tokens；协调器正常接受 unknown / insufficient_evidence，缺少运行、日志及实际部署配置证据。第二次有取证余量时主动结束；两次轨迹不同，不能据此声称该题固定需要超过 300,000 tokens。无平台发送、登记或正式入口开放。

### 2026-09-15：按 Provider 模型窗口限制 Bug 上下文

不增加 Bug 专用的上下文窗口配置。共享模型绑定直接读取 Pydantic AI 已解析模型的 `model.context_window`；Bug Agent 从中预留本轮配置的最大输出额度，把剩余空间作为单次输入上限。窗口会进入资格预算指纹。自定义 Provider 地址和 profile 无法识别的模型不套用公开同名模型的窗口，避免把错误能力写进运行合同。

Pydantic AI 当前不能在 OpenAI Chat 请求前为 DeepSeek 本地计数，因此该限制会在 Provider 已成功返回 usage 后生效：当前响应仍可处理，如果还需要下一轮工具或修正请求，则在发送前停止。Provider 自身仍负责拒绝真正超出硬窗口的当前请求。这个边界防止多轮调查继续扩大已经过长的上下文，不用于降低一次调查的累计费用；累计 token 和工具次数继续承担总消耗控制。DeepSeek V4 Flash 当前元数据为 1,000,000 tokens，上限扣除默认 16,384 输出后是 983,616 input tokens，所以此前 v8 最大单次输入 36,418 不会受影响，其 357,049 累计输入来自多轮重复携带上下文，仍需通过取证方向和调用次数另行观察。

### 2026-09-15：固定单次 Bug 调查的工具定义

项目作者接受把工具可见性与运行额度分开：本轮开始时确实没有 loader 或源码根的工具仍不下发；已经下发的直接证据、源码导航和只读文件工具不再因额度耗尽、单类次数用完、聊天窗口读完或定义跳转状态变化而从后续请求消失。对应限制改在工具执行层检查，额度或次数用完时返回结构化 `unavailable` 原因，路径或 revision 等可纠正调用错误继续使用既有 `ModelRetry`；通用额度、单类次数、批准根、路径、revision 与证据正文限制保持不变。这一实现更新替代本 ADR 及 ADR-0135 中“耗尽后隐藏工具”的旧落实方式。

维护诊断在每个 Provider 请求开始时记录排序后的 function/output 工具名和完整定义的规范化 SHA-256，不保存 Schema 正文。该记录用于判断本轮工具前缀是否实际稳定；哈希相同只证明工具定义一致，不直接证明 Provider 一定命中缓存。真实搜图贯通评测会把这些生命周期事件写入隔离报告，再与各轮 cache token 对照。

同日仅重跑真实搜图生产观察场景。12 次 Bug Provider 请求的工具名称和完整定义哈希全部一致；Provider 报告的累计输入 347,919 tokens，其中 cache read 321,536，命中率 92.4%，未命中 26,383。对照改动前 v8 的 16 次请求、累计输入 357,049、cache read 269,696、命中率 75.5% 和未命中 87,353，说明动态工具定义确实是此前两轮大幅缓存失效的来源之一。两次轨迹与请求数不同，因此该对照不能量化固定工具定义的独立节省，也没有减少多轮累计 token 的预算计数。

本次模型读取了锁实现、`@async_lock(freq=8)` 与限流递归源码，却最终返回 `unknown / insufficient_evidence`，严格正例断言保留失败；没有建档。该结果不否定工具定义与缓存验证，但说明真实模型对“独立源码足以确认实现缺陷”的判断仍有波动，后续应作为调查质量问题单独处理，不继续修改本次预算或工具可见性设计。
