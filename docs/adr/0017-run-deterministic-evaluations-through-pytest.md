# ADR-0017：通过 pytest 执行确定性评测回归

## 状态

已采纳

## 日期

2026-08-10

## 当时遇到了什么

公开仓库需要在代码变更后自动发现 Agent 领域行为退化。当前项目已经把固定合成 Fixture、rubric、split、
scripted model 行为和少量冻结结果作为版本化评测合同，并用 pytest 验证 evaluator、指标门和报告 schema。
现有 GitHub Actions 也已经在 Python 版本矩阵运行全部 pytest。

这里的确定性评测测试是指：不调用真实模型和网络，不读取维护者本地数据或凭据；同一份代码、版本化输入
和固定测试替身重复运行时，应产生相同的结构化结果。它比单个函数的普通单元测试更接近完整评测场景，
但仍然属于可重复的自动化回归测试，不能证明真实模型的回答质量或稳定性。

曾考虑为这些评测再增加独立 `ci-evals` job、GitHub Step Summary 和短期 JSON Artifact。但在当前规模下，
这会与 pytest 已有覆盖重复，并额外引入聚合入口、报告脱敏、Artifact 上传和工作流维护成本。

## 最后决定

1. 确定性评测通过现有 pytest 测试进入公共 CI，不新增独立 `ci-evals` job。
2. 进入公共 CI 的评测必须只使用 Git 中经过复核的合成 Fixture、rubric、split、固定测试替身和公开最小
   合同；不得访问网络、真实 Provider、密钥、生产日志、`data/`、MLflow 状态或维护者本地索引。
3. 测试可以调用完整 evaluator、验证聚合指标和硬门，也可以比较经过复核的冻结结果；任一契约或门禁回归
   都直接表现为 pytest 失败，并由现有 `test` job 阻止合并。
4. 公共 CI 不为每次运行生成或上传完整评测 JSON，不写专用指标摘要，也不把机器运行结果提交回 Git。
   失败时先使用 pytest 的断言定位，并在本地复现相同固定输入。
5. 需要长期比较的完整评测运行由维护者在本地执行并记录到 MLflow；真实模型 Gate 仍需显式模型、预算、
   数据出站和凭据授权，不能由公开 PR 自动触发。
6. 只有出现以下至少一项实际需求时，才重新评估是否拆出专用 job：确定性评测耗时需要与多 Python 版本
   测试分离；外部 PR 评审确实需要独立指标摘要；pytest 失败信息不足以诊断指标变化；或者公共评测集合已经
   大到需要独立资源、超时和保留策略。

## 为什么这样选

- 当前 CI 已经运行全部 pytest，确定性评测测试无需新增工作流就能形成自动回归门禁；
- 失败断言与 evaluator 测试放在一起，维护者可以直接在本地复现，不需要先下载一次性 Artifact；
- 避免为尚未出现的外部协作和报告消费需求维护聚合命令、摘要白名单与上传策略；
- 明确把可重复的合成回归与有费用、有随机性、需要凭据的真实模型评测分开。

## 没有采用的方案

- **立即增加独立 `ci-evals` job 和短期 Artifact**：当前与 pytest 覆盖重复，额外体验收益不足以抵消维护
  成本；达到本 ADR 列出的触发条件后可以重新评估。
- **每次把机器报告提交到 `evals/snapshots/`**：会持续增长 Git 历史，也会混淆版本化评测合同与运行结果。
- **在公共 PR 自动运行真实模型 Gate**：无法安全处理 fork 权限、密钥、费用、随机性和数据出站确认。

## 带来的影响

- PR 页面只有现有 pytest job 的通过或失败状态，不提供独立评测卡片、指标摘要或报告下载；
- 当前小规模确定性评测会随 pytest 在 Python 3.11–3.14 重复运行，先换取最简单的工作流；如果耗时成为
  实际问题，再按已记录的触发条件拆分；
- MLflow 继续负责维护者本地的跨版本实验历史，GitHub Actions 不承担评测结果数据库职责；
- 新增确定性 evaluator 时必须同时增加可重复的 pytest 覆盖，不能只提供需要人工执行的命令。

## 落实与确认

- 实施情况：现有 `.github/workflows/ci.yml` 的 `test` job 已运行完整 pytest；当前仓库已有 B0 冻结结果、
  S3 合成安全、B3 结构化回执、answer-quality rubric 校准和 B4 scripted Gate 等确定性测试。
- 尚未增加也不需要增加 `ci-evals` 聚合入口、指标摘要脚本或评测 Artifact 上传步骤。
